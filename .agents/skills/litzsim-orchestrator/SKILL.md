# LitzSim Orchestrator

여러 이슈를 작업자 agent에게 나눠 맡기고, 결과 PR을 확인해 `main`에 병합하는 통합 담당자 절차다. 오케스트레이터는 직접 제품 코드를 고치지 않는다. 판단, 배정, 확인, 로컬 검증, 병합, 정리를 맡는다. 사용자에게는 한국어로 보고한다.

이 스킬은 `litzio/litzio`의 `litzio-orchestrator`를 LitzSim에 맞게 옮긴 것이다. 가장 큰 차이는 **CI와 merge queue가 없다**는 점이다([MVP 계획](../../../docs/mvp.md)에서 GitHub CI 도입을 보류했다). 그래서 queue가 하던 "병합 결과 검사"를 오케스트레이터가 [pr-verify.mjs](scripts/pr-verify.mjs)로 직접 한다. 병합 결과(현재 `main` + PR head)를 Release로 빌드하고 CTest 전체를 통과했다는 기록이 없으면 병합하지 않는다.

이 스킬은 모델과 하네스에 의존하지 않는다. 작업자 생성·메시지·상태 확인은 Paseo MCP 도구가 있으면 그것을, 없으면 `paseo` CLI를 쓴다. 사용법은 전역 `paseo` 스킬을 따른다. 스크립트 경로는 이 SKILL.md가 있는 폴더 기준이다.

## 0. 적용 범위 확인

- `git remote get-url origin`이 `github.com/litzio/litzsim`이 아니면 즉시 멈추고 이 스킬은 이 저장소 전용이라고 알린다.
- 사용자가 이 스킬을 명시적으로 호출한 경우에만 쓴다. 단일 이슈를 직접 구현하는 일에는 쓰지 않는다.
- 저장소 규칙의 우선순위는 사용자 지시 → [AGENTS.md](../../../AGENTS.md) → [제품 목적](../../../docs/purpose.md)·[문서 색인](../../../docs/README.md)에 연결된 문서 → 이 스킬이다. 충돌하면 사용자에게 어떤 규칙에서 벗어나는지 밝힌다.

## 지휘 원칙 (모든 단계 공통)

**멈추지 않는다.** 하네스는 턴이 끝나면 다음 알림이나 사용자 메시지가 올 때까지 오케스트레이터를 깨우지 않는다. 턴을 끝내기 전에 다음을 확인한다.

- 진행 중인 항목마다 오케스트레이터를 다시 깨울 장치가 걸려 있다. 작업자·리뷰어의 완료 알림(notifyOnFinish) 또는 직접 시작한 백그라운드 검증(`pr-verify.mjs`)이 그 장치다.
- 오케스트레이터가 내릴 결정이 남아 있지 않다. 남아 있으면 지금 결정하고 지시를 보낸 뒤 끝낸다.
- 병합·작업자 보고·리뷰 결과 같은 중간 완료를 받았으면, 같은 턴에서 다음 할 일(다음 이슈 배정, 다른 PR의 재검증, 정리)까지 시작했다.

**판단은 오케스트레이터가 내린다.** 승인된 결정 범위 안의 판단은 사용자나 작업자에게 넘기지 않는다. 진단 실행 여부, 테스트 최소 수정 방향, 재실행 여부, 리뷰 필요 여부가 여기에 속한다. 작업자에게 조사를 맡길 때는 범위와 끝낼 기준(무엇이 확인되면 어떤 조치로 갈지)을 함께 준다. 결과가 오면 그 턴에 판정한다. 사용자에게는 결정 범위 밖의 제품 판단만 묻는다. 물을 때는 제품 질문 하나로 묻는다: 엔지니어에게 무엇이 달라지는가, 판단에 필요한 사실 두세 가지, 하지 않으면 어떻게 되는가, 추천. 구현 방법의 선택지(어느 자료구조, 어느 적분법의 내부 구현)는 묻지 않고 정한다. 다만 **해석 결과를 바꾸는 모델 선택**(적분법, 소자 모델의 이상화 수준, 허용오차)은 제품 판단이므로 묻는다.

**보고 형식.**
- 사용자에게는 한국어로만 보고한다.
- 질문에는 일반 문장으로 답하고, 응답 끝에 지휘 중인 작업의 현황 표 하나를 둔다. 표 위아래에는 빈 줄을 둔다.
- 표에는 진행 중인 작업과, 이미 승인돼 순서가 정해진 예정 작업("예정, ○○ 뒤")만 넣는다. 항목 칸에는 번호와 짧은 설명, 작업자 모델을 함께 쓴다. 보류와 아직 정하지 않은 다음 후보는 넣지 않는다.
- 바뀐 것이 없는 "대기 중" 보고를 반복하지 않는다. 소유자의 조치나 결정이 필요 없는 중간 사건(작업자의 중간 보고, 충돌 해결, 재투입, 되돌려 보낸 수정)은 따로 보고하지 않고, 병합·실패·소유자가 알아야 할 사실과 함께 묶어 알린다.
- **간소화 모드.** 사용자가 `#간소화 모드`라고 보내면 켠다. 켜진 동안에는 중간 완료·병합·작업자 배정을 스스로 보고하지 않고, 현황 표와 설명도 붙이지 않는다. 사용자에게 말을 거는 것은 결정 범위 밖의 판단이 필요해 물어야 할 때뿐이다. 턴을 끝낼 때 글이 필요하면 한 줄로 쓴다. 지휘 원칙과 검증·병합·정리 절차는 그대로 지킨다. 사용자가 질문하거나 보고를 요청하면 해제한다.

**작업자 지시 문장.**
- 작업자·리뷰어에게는 띄어쓰기를 지킨 정상 문장으로 지시한다. 식별자를 붙여 쓴 압축 문장은 쓰지 않는다.
- 단순 상태 보고에 수신 확인 답신을 보내지 않는다. 같은 지시를 다시 보내지 않는다.

**완료 전달.**
- 작업자·리뷰어에게 작업을 배정하거나 후속 작업을 맡길 때 `notifyOnFinish: true`를 유지한다. 완료 보고는 agent의 최종 답변에 한 번만 작성하고 Paseo의 자동 finish 알림으로 받는다. 같은 완료 보고를 `send_agent_prompt`나 CLI 메시지로 별도 전송하게 하지 않는다.
- 작업자가 부모 또는 동료에게 보내는 직접 메시지는 중간 질문·차단 사항·진행에 필요한 인계에만 쓴다. 상대의 `serverId`를 확인한 뒤 `notifyOnFinish: false`로 보낸다.
- 직접 보고와 자동 알림이 모두 도착하면 source agent ID와 배정한 작업·PR head·결과를 대조해 같은 완료는 한 건으로 처리한다.

**과설계를 막는다.** LitzSim은 1차 MVP 이후의 컨셉 검증 단계다. 새 추상화·상태·계층·플러그인 구조·범용 엔진은 "지금 막힌 실제 사례" 한 문장이 없으면 나중으로 미룬다. 추가보다 삭제·연기·기존 것 재사용을 우선한다.
- Astra 계열 모델은 독립 리뷰(위험 PR), 읽기 전용 상담, 원인 조사가 중심인 좁은 결함(수치 발산, 간헐 실패)의 조사·수정에 쓴다. 설계 문서 작성, 해석기 구조 일반화, 여러 화면에 걸친 구현은 맡기지 않는다(litzio에서 일반화한 설계가 곧 제거된 사례가 있다).
- 상담 프롬프트에는 컨셉 검증 단계임을 밝히고, 소유자 확정 결정을 재론하지 못하게 하며, 답의 길이(40~60줄)와 형식(판정 표, 하나의 추천안)을 고정한다.
- 리뷰 결과를 받으면 차단 지적마다 "이 수정이 모델·상태·파일 규격을 키우는가"를 확인한다. 키운다면 구현자에게 넘기기 전에 더 단순한 대안(그 입력을 거부, 지원 범위에서 제외하고 오류로 안내, 기존 연산 재사용)을 먼저 정한다. 같은 PR에서 리뷰 두 차례 연속으로 새 상태·필드가 늘면 수정 지시를 멈추고 설계를 단순화할지 사용자에게 보고한다.
- 리뷰어 프롬프트에는 [reviewer-prompt.md](references/reviewer-prompt.md)의 과설계 금지 절을 그대로 둔다.

**인계받을 때.** 다른 오케스트레이터가 만든 작업자의 완료 알림은 새 오케스트레이터에게 오지 않는다. 진행 중인 작업자와 리뷰어마다 `send_agent_prompt`(notifyOnFinish: true)로 "현재 상태를 짧게 보고하고 하던 일을 계속하라"를 보내 알림을 넘겨받는다.

## 1. 시작 전에 사용자에게 확정받을 것

추천안을 함께 제시하고 한 번에 확정받는다. "추천안대로"라는 답도 승인으로 본다.

- **범위:** 대상 이슈 목록. 열린 이슈는 `gh issue list --state open --json number,title,labels`로 확인한다. 사용자가 이슈 없이 작업을 말로 주면, 작업마다 이슈 초안(제목, 완료 기준, 검증 조건)을 계획 표에 함께 보이고 승인받은 뒤 등록한다. 규모가 큰 기능, 원인이 확정되지 않은 수치 결함, 결정이 필요한 항목은 이번 범위에서 빼거나 결정만 받는 후보로 분류한다.
- **결정:** 해석 결과를 바꾸는 선택(모델·적분법·허용오차·지원 토폴로지), `*.litzsim` 파일 규격 변경, 사람과 AI가 공유하는 단자·측정 방향 규약의 변경은 추천안을 쓰고 승인받는다. 승인 전에는 구현을 맡기지 않는다.
- **작업자 모델:** 사용자가 지정한 provider/model을 우선한다. 쓰지 말라고 한 provider는 어떤 단계에서도 쓰지 않는다. 지정이 없으면 litzio 소유자 결정(2026-11-23)을 이어 쓴다: 구현 작업자는 Codex `gpt-6.2-sol`과 Claude `claude-opus-5-5` 가운데 일에 맞게 나눠 쓰고, `gpt-6.2-astra` medium은 위 과설계 절의 범위에서만 쓴다. 독립 리뷰어의 기본은 `gpt-6.2-sol`이며, 리뷰할 PR의 구현과 다른 모델을 우선한다. Claude 작업자는 mode `bypassPermissions`로 만들고, 지시문에 trailer 예상 값(`AI-Agent: Claude Code`, `AI-Model: anthropic/claude-opus-5-5`)과 "하네스가 권하는 Co-Authored-By 줄은 넣지 않는다"를 적는다. Fast(`service_tier`)는 켜지 않는다. effort 기본값은 medium(작은 UI·문구, 재현이 명확한 작은 버그) 또는 high(해석기·소자 모델·파일 규격·편집 연산)다. xhigh는 같은 작업에서 high가 실제로 부족했다는 근거를 소유자에게 보고한 뒤에만 쓴다. 스스로 하위 agent를 만드는 설정은 쓰지 않는다.
- **모델 id 확인:** 작업자를 만들기 전에 Paseo의 모델 목록에서 id를 확인하고, trailer 예상 값도 그 id로 지시문에 적는다(예: `AI-Model: openai/gpt-6.2-sol`). 사용자가 지정한 모델·추론 강도는 지정한 범위에만 쓴다.
- **리뷰 범위:** 기본은 5절의 위험 기준이다. 위험 PR에만 독립 리뷰를 붙이고 나머지는 오케스트레이터 확인 기록으로 승인한다. 사용자가 모든 PR 리뷰를 원하면 따른다.
- **병합 권한:** 조건을 만족한 PR을 오케스트레이터가 `main`에 병합해도 되는지, 화면 변경은 소유자가 캡처를 본 뒤 병합할지 확인한다.

## 2. 계획

1. 이슈 본문과 관련 문서([제품 목적](../../../docs/purpose.md), [MVP 범위](../../../docs/mvp.md), [검증 기록](../../../docs/reviews/pfc-validation.md), `docs/spikes/`)를 읽는다. 주장하는 사실은 코드로 확인한다.
2. 이슈마다 고칠 파일을 예상하고, 같은 파일을 고치는 이슈끼리 선후를 정한다. 이 저장소는 파일이 적고 한 파일의 책임이 넓어서 충돌이 잦다. 특히 `src/circuit.*`(파일 규격·단자·네트), `src/solver.cpp`, `src/pfc.cpp`, `src/schematic.cpp`, `src/studio.*`, `src/viewer.*`, `CMakeLists.txt`(테스트 등록), `examples/*.litzsim`, `README.md`, `docs/reviews/pfc-validation.md`는 한 번에 한 PR만 고치게 순서를 정하거나 한 PR로 묶는다. 여러 PR이 같은 문서의 같은 절을 고치게 되면 그 문장 변경은 마지막 PR 하나에 모은다.
3. 결정 없이 시작할 수 있고 서로 겹치지 않는 이슈를 1차로, 나머지를 선행 PR 병합 순서대로 배치한다. 동시에 실행하는 작업자와 리뷰어는 4명 이하로 둔다. 실제 제약은 같은 파일 충돌과 PC 자원이다. 작업자마다 C++/Qt를 처음부터 빌드하고, 오케스트레이터의 병합 검증도 같은 PC에서 빌드한다.
4. 계획을 표로 보고한다(이슈, 작업자 모델·effort, 주로 고칠 파일, 선행 조건, 독립 리뷰 여부). 제외한 이슈와 이유도 쓴다.
5. 해석 방식이나 화면 방향을 사용자가 골라야 하는 제안은 바로 구현하지 않는다. 병합하지 않는 `spike/<번호>-…` 브랜치에서 비교 실행이나 시안을 만들고, 결과를 `docs/spikes/`에 기록하는 문서 PR과 이슈 댓글로 고르게 한다. 스파이크 코드는 병합하지 않는다. 채택된 안은 이슈를 등록해 `main` 기준으로 다시 구현하게 한다.

## 3. 작업자 실행

- 이슈마다 새 Paseo worktree를 `baseBranch: "origin/main"`에서 branch-off로 만든다(로컬 `main`은 낡았을 수 있다). 브랜치 이름은 기존 관례대로 `feat/…`, `fix/…`, `docs/…`를 쓴다. 병합 직후의 worktree를 재사용하지 않는다. 선행 PR의 head에서 갈라 미리 시작시키는 것은 선행 PR이 승인돼 병합 검증 중일 때만 하고, 지시문 첫 문단에 선행 PR 번호와 "선행 PR이 병합되면 origin/main을 merge한 뒤 PR을 만든다. 30분이 지나도 병합되지 않으면 보고한다"를 넣는다.
- 지시문에 그 이슈의 **로컬 검사 명령**을 적는다. 기본은 README의 Release 빌드와 `ctest --test-dir build --output-on-failure` 전체다. 빌드 셸의 PATH 앞에 MSYS2 UCRT64의 `bin`을 둔다. 해석기·소자 모델을 바꾸면 이에 더해 검증 기록과 같은 조건의 비교 실행(`litzsim-cli run`)을 적는다. 각 worktree는 자기 `build/`를 쓴다(다른 checkout의 빌드 폴더를 공유하지 않는다).
- 지시문에 적는 사실 전제(이미 되는 동작, 지원하는 결선, 검사가 쓰는 예제 파일)는 코드나 문서로 확인한 뒤 쓴다. 확인하지 않은 전제는 "확인 필요"로 표시한다.
- 작업자는 쓰기와 네트워크가 가능한 모드로 만든다. 지시문은 파일 쓰기 도구로 파일에 쓰고, 공통 규칙은 띄울 때마다 [worker-prompt.md](references/worker-prompt.md)의 블록을 그 파일에서 읽어 그대로 붙인다. 줄이거나 고친 세션 사본을 돌려쓰지 않는다. 공통 규칙이 모자라거나 길면 worker-prompt.md를 고치는 PR을 낸다.
- **작업자 한 명은 PR 하나만 맡는다.** PR이 병합되면 그 작업자의 일은 끝난다. 같은 작업자에게 이어서 맡기는 것은 같은 PR의 리뷰 지적 반영, 충돌 해결, 병합 검증 실패 수정, 한 이슈를 나눈 바로 다음 조각일 때만 한다. 이어서 맡기기 전에 컨텍스트 사용량(`get_agent_status`의 `contextWindowUsedTokens`)을 확인하고 절반을 넘었으면 새 작업자로 바꾼다.
- 만든 뒤 1–2분 지나서 상태가 `running`인지, worktree가 실제로 있는지 직접 확인한다. 알림이 없다는 이유로 "진행 중"이라고 보고하지 않는다.
- 작업자가 모델 용량 오류로 멈추면 같은 agent에 "`git status`, 최근 커밋, 열린 PR을 확인한 뒤 이어서 진행하라"를 보낸다. 새 agent로 교체하지 않는다.
- 작업자가 결정이 필요하다고 멈추면, 승인된 결정 범위에서 답할 수 있으면 근거와 함께 답한다. 범위 밖이면 사용자에게 묻는다.
- 실행 중인 작업자에게 범위를 더하는 것은 같은 파일을 고치고 같은 이슈의 완료 기준에 속할 때만 한다. 성격이 다른 동작 변경(파일 규격·해석 결과·편집 연산)은 새 이슈와 새 작업자로 나눈다.

## 4. PR이 올라왔을 때

1. `gh pr view <N> --json files`와 `gh pr diff <N>`로 diff를 직접 읽는다. 확인할 것:
   - 범위 밖 변경, 테스트 단언 약화(삭제·허용오차 확대·기준값을 결과에 맞춰 고침·timeout 증가·재시도), 승인된 결정과의 일치.
   - **공통 코어 원칙.** 단자·연결·측정 방향과 편집 연산을 GUI(`studio`·`schematic`)나 CLI에서 따로 구현하지 않았는지. 같은 연산을 공통 코어에 두고 양쪽이 호출해야 한다.
   - **모델 변경의 검증 근거.** 해석기·소자 모델·PFC 축약 방정식이 바뀌었으면 PR 본문에 같은 회로·제어·초기조건에서의 전후 비교, 정확도 수치와 실행시간, 측정 조건, 미검증 범위가 있는지. 기준해·허용오차를 결과를 본 뒤에 정하지 않았는지.
   - **파일 규격.** `*.litzsim` 필드가 바뀌면 `version`, 예제 파일, README의 규격 설명, 저장→재열기 시험이 함께 바뀌었는지.
   - 삭제·이름 변경 PR은 지운 이름을 직접 `git grep`해 PR 본문 결과와 대조한다.
   - README의 기능 설명은 실제로 실행하고 확인한 것만 쓰는지([제품 목적](../../../docs/purpose.md) 마지막 문장).
2. 화면 변경은 캡처가 나오는 즉시 직접 본다. `git fetch origin pull/<N>/head:pr-<N>` 뒤 `git show pr-<N>:<캡처 경로> > <scratch>/x.png`로 꺼내 확인한다. [MVP 계획의 화면 변경 검토](../../../docs/mvp.md) 기준(리치오와 같은 논리 해상도·배율 비교, 단자·측정 방향 표시, 파형 축·범례·피크 가독성)을 적용한다. 캡처에 계정 이름·PC 이름·로컬 경로가 보이면 추가 push를 멈추게 하고 소유자에게 사실대로 보고한다.
3. 작업자의 검사 실패 보고는 다음 순서로 판정한다.
   1. 같은 증상의 기존 이슈와 소유자 결정을 찾는다(`gh issue list --state all --search "<시험 이름>"`).
   2. 제품 결함·검사 전제 오류·원인 미확정으로 가른다. 반복 실행에서 재현되지 않았다는 것은 원인 확정이 아니다.
   3. 수치 결과가 기준을 벗어나면 기준을 바꾸지 않고 원인을 찾는다. 기준 자체가 틀렸다는 근거(해석해 재유도, 독립 계산)가 있을 때만 기준을 고치고, 그 근거를 PR 본문에 쓴다.
   4. Qt GUI 시험(`studio`, `viewer`, `pfc-studio`, `workflow`)이 기계 속도에서만 실패하면 실제 상태를 기다리게 고친다. 단언 삭제·완화, 재시도, timeout 증가는 하지 않는다.
4. 리뷰가 필요하면 5절대로 리뷰어를 붙인다. 필요 없으면 6절로 간다.

## 5. 독립 리뷰

- 붙이는 기준(위험 PR): 해석기·소자 모델·적분·PFC 축약 방정식, `*.litzsim` 규격과 직렬화·저장 경로, 단자·네트·프로브 극성과 편집 연산(공통 코어), 실행 스냅샷(`runs/`)과 재현성, 대용량 파형 저장·요약(피크 보존), Windows 런타임 배치(`cmake/`), 파일 삭제·이동이 있는 탐색기 동작. 작은 UI·문구·테스트만·문서만의 수정은 오케스트레이터 확인으로 대신한다.
- 리뷰어는 구현에 참여하지 않은 새 agent이고, 프롬프트는 [reviewer-prompt.md](references/reviewer-prompt.md)를 쓴다. 이 PR에서 특히 위험한 지점을 중점 확인 항목으로 구체적으로 적는다.
- 리뷰어는 구현자의 worktree를 같이 쓰며 별도 빌드 폴더(`build-review/`)를 쓴다. 리뷰어가 도는 동안 구현자에게 수정·push를 맡기지 않는다.
- 리뷰 중 구현자가 head를 바꾸면 리뷰어에게 최종 head 기준으로 판정하라고 알린다.
- `REQUEST_CHANGES`면 차단 지적마다 오케스트레이터가 먼저 "엔지니어가 실제로 낼 수 있는 회로·조작에서 생기는가, 결과가 틀리거나 데이터를 잃는가"를 따진다. 아니면 비차단 메모로 내리고 그 판단을 기록에 쓴다. 남은 지적만 구현자에게 전달하고, 수정 후 같은 리뷰어 또는 새 리뷰어에게 재검토를 맡긴다.
- 같은 종류의 지적(예: 지원하지 않는 결선의 또 다른 변형)이 라운드마다 이어지면, 오케스트레이터가 보장 범위를 정해 문장으로 고정한다. 예: "PFC 해석은 예제의 결선만 지원하고, 그 밖의 결선은 해당 소자 ID를 밝힌 오류로 거부한다." 재리뷰 지시에는 그 범위 밖 경로를 비차단 메모로 두라고 적는다.

## 6. 병합

CI가 없으므로 병합 결과의 검증은 오케스트레이터가 한다. 순서는 **검증 → 확인 → 병합**이고, 병합은 한 번에 하나씩 한다.

```bash
node <skill>/scripts/pr-verify.mjs --pr <N>          # 현재 origin/main + PR head를 임시 worktree에서 Release 빌드·CTest
node <skill>/scripts/pr-gate.mjs --pr <N>            # 병합 조건만 확인
node <skill>/scripts/pr-gate.mjs --pr <N> --merge --note-file <note.md> --ai-agent "<도구>" --ai-model "<provider>/<model>"
```

- `pr-verify`는 몇 분 걸릴 수 있으므로 완료 알림이 오는 백그라운드 실행으로 돌린다(그런 기능이 없는 하네스에서는 그 PR의 작업자에게 실행과 결과 보고를 맡긴다). 성공하면 마지막 줄에 `로컬 검증: head <sha> on main <sha> — …` 한 줄을 출력한다. 이 줄을 기록 파일에 그대로 옮긴다. 임시 worktree는 끝나면 스스로 지운다.
- 기록 파일의 첫 줄은 `독립 리뷰: APPROVE <head>` 또는 `독립 리뷰: 생략 — <5절 기준에 비춘 사유>`다. 다음 줄에 `작업자: <모델> <추론 강도> / 리뷰어: <모델> <추론 강도 또는 없음>`, 이어서 `로컬 검증:` 줄, 오케스트레이터가 확인한 것을 쓴다.
- `pr-gate`는 저장소, 열린 PR, base `main`, Draft 여부, 충돌, PR head와 원격 브랜치 일치, 미해결 review thread 0, 범위 안 모든 커밋의 `AI-Agent`·`AI-Model` trailer, 기록 파일의 리뷰 판정 줄, 그리고 **기록의 `로컬 검증` 줄이 지금의 PR head와 지금의 `origin/main`을 가리키는지**를 확인한다. 하나라도 실패하면 병합하지 않는다. 나중에 GitHub 검사가 생기면 실패·대기 중인 검사도 막는다.
- `--merge`는 기록을 PR 댓글로 남기고 `gh pr merge --merge --match-head-commit <head>`로 병합한다. merge 커밋 본문에는 PR 제목과 오케스트레이터의 `AI-Agent`·`AI-Model` trailer를 넣는다(AGENTS.md). 병합 뒤 `state: MERGED`를 확인해 출력한다.
- **한 PR이 병합되면 `main`이 움직였으므로 다른 모든 PR의 `로컬 검증` 줄은 무효가 된다.** 다음 PR은 `pr-verify`부터 다시 한다. 충돌이 나면 원래 작업자에게 `origin/main` merge와 충돌 해결을 맡기며, 앞서 병합된 PR이 무엇을 바꿨는지 함께 알려 준다. 충돌이 없는데 병합 결과의 시험만 실패하면, 이 PR의 문제인지 앞서 병합된 PR과의 상호작용인지 가르고 원래 작업자에게 판정·수정을 맡긴다.
- 승인 뒤 head가 바뀐 경우: 위험 PR에서 제품 코드나 테스트 단언이 바뀌었으면 새 APPROVE를 받는다. 충돌 해결, 문서만의 변경은 리뷰어를 다시 부르지 않고 `git show --remerge-diff <merge>`와 추가 diff를 직접 확인한다. 어느 쪽이든 `pr-verify`는 다시 한다.
- 원격 브랜치는 `gh pr view <N> --json state`가 `MERGED`인 것을 확인한 뒤에만 지운다. 병합과 삭제를 `;`로 잇지 않는다.

## 7. 정리와 보고

- PR이 병합된 것을 `state: MERGED`로 확인한 뒤에만 그 worktree를 archive한다(작업자와 리뷰어 포함). 결과만 남기고 끝난 조사·스파이크 작업자는 결과를 확인한 뒤 archive한다.
- worktree를 archive하기 전에 그 폴더 안에 worktree 밖(특히 주 checkout)을 가리키는 junction·심볼릭 링크가 있는지 확인한다(PowerShell `Get-ChildItem <worktree> -Recurse -Force -Attributes ReparsePoint`에서 Target이 worktree 밖인 것). 있으면 링크 항목만 먼저 지운다(재귀 삭제 금지). litzio에서 archive가 링크를 따라가 주 checkout의 추적 파일을 지운 사고가 있었다. 병합이나 archive 뒤 주 checkout은 `git status --short`의 줄 수가 0인지로 확인한다.
- 하나의 PR이 병합될 때마다, 병합을 확인한 그 턴에서 맞물린 다음 작업을 시작한다(선행 조건이 풀린 이슈의 작업자 배정, 다음 PR의 `pr-verify`). 병합 보고만 하고 멈추지 않는다.
- 세션에서 얻은 지휘 교훈(지시문의 빈 곳, 빠진 확인, 새 공통 규칙)은 세션을 끝내기 전에 이 스킬과 `references/`를 고치는 PR로 올리고 바뀐 문장을 소유자에게 보인다. 더할 때는 지울 조항을 함께 찾는다.
- 끝나면 확인한다: 대상 이슈의 상태, 열린 PR, 남은 worktree와 작업자, 남은 임시 검증 worktree(`git worktree list`). 직접 시작한 백그라운드 실행도 종료한다.
- 최종 보고: 병합한 이슈·PR 표(리뷰 여부, 로컬 검증 결과 포함), 저장소 절차에서 벗어난 점, 남은 일과 확인하지 못한 것(외부 기준 파형 대조, 실기, 실제 모니터 표시 등), 리뷰의 비차단 메모, 처음 나온 간헐 실패, 정리 상태.
