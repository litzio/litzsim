# 웹 파형 표시 스파이크

2026-11-26 · [이슈 #24](https://github.com/litzio/litzsim/issues/24) · [1차 실험 코드 8f012cdccbd15e2d2f1082c693f770dcea161361](https://github.com/litzio/litzsim/commit/8f012cdccbd15e2d2f1082c693f770dcea161361) · [후속 실험 코드 986503f31411bab8570bb4b5caf5bac201c93cf8](https://github.com/litzio/litzsim/commit/986503f31411bab8570bb4b5caf5bac201c93cf8)

엔진 파일과 CSV 변환본 모두 4개 시간 plot의 첫 표시와 피크·XY 정확도 기준을 충족했다. 이동·확대의 정확한 프레임 p95는 1차 71.8–72.2 ms였고, 후속 시험에서 응답 직후 그리기로 53.5–53.8 ms까지 줄었다. 33 ms 기준은 두 형식 모두 미달했다. Qt 뷰어는 웹 인수 조건을 통과할 때까지 유지한다.

## 구현과 비교 조건

- 브라우저는 React로 시간 plot 4개와 XY plot 하나를 Canvas에 그린다. 앱 수명의 Node 프로세스가 루프백 HTTP를 제공하고 기존 CLI 자식 하나와 줄 단위 요청·응답을 주고받는다. 응답의 JSON 본문을 Node에서 다시 파싱하거나 생성하지 않는다. 이 구성은 브라우저에서 로컬 계층 호출을 시험하면서 같은 `Waves` 파일 매핑과 채널별 요약을 요청 사이에 재사용한다.
- 시간 plot은 `envelopeRows`가 반환한 원래 행·시각·값을 받는다. 이전 범위의 응답은 새 입력이 들어오면 그리기에 쓰지 않는다. XY는 기존 Qt와 같이 두 신호의 극값 행을 취득 순서대로 합집합한 뒤 같은 행의 X·Y를 읽는다. XY에는 전체 취득 구간의 요약을 한 번 요청하며, 시간 plot의 이동·확대는 XY를 다시 그리지 않는다.
- Windows 11 Pro 26200, Ryzen 5 5600X, RAM 32 GiB, Samsung SSD 980 PRO, RTX 3070 Ti, 화면 2560×1440 @ 60 Hz. Windows 시스템 DPI는 192(200%). 브라우저 뷰포트와 Qt 렌더는 1280×780, DPR 1 조건이다. UCRT64 GCC 15.2.0, Qt 6.10.1, Ninja Release, Node 24.22.3, Vite 8.3.8 프로덕션 번들, Playwright 1.65.1, Chromium 159.0.8154.6을 사용했다.
- `wave-test`의 합성 방식대로 시간 열과 신호 8개, 총 1,000만 행을 생성했다. `a`는 256번 행에서만 23이며, `b/c`에는 512–515번 행에 비단조 XY 루프를 추가했다. CSV는 238,888,916 B이며 생성 직후 첫 변환과 인덱스 쓰기에 17.852 s가 걸렸다. 엔진 형식과 CSV 변환본은 각각 721,410,364 B이고 SHA-256이 일치했다. 모든 표시 측정은 각 시험 직전에 준비 파일을 순차 읽기한 warm OS cache 조건이다. 웹은 매회 새 Node·CLI와 브라우저를 띄워 HTTP 캐시와 메모리 내 채널 요약을 비운 상태에서 시작했다.

## 첫 표시와 입력 응답

웹은 Windows headful Chromium을 사용했다. 실제 창의 렌더링 일정에서 입력 이벤트 시각부터 Canvas를 그린 다음 `requestAnimationFrame` 콜백까지 재기 위해 이 모드를 택했다. 첫 표시에는 탐색 시작부터 번들 로드, 자식 기동·매핑, 첫 요약 요청과 4개 시간 plot의 프레임이 포함된다. XY는 첫 표시 뒤 별도로 그렸다. 각 시험에서 실제 포인터 드래그와 휠 입력을 25회씩 번갈아 보내고, 해당 입력의 새 범위가 렌더된 뒤 다음 입력을 보냈다. p95는 각 50회의 48번째 순위다.

Qt는 동일한 파일, 동일한 네 채널과 브라우저에서 기록한 50개 시간 범위로 기존 QWidget 벤치마크를 실행했다. 첫 표시 시간은 뷰어의 파일 열기부터 4개 plot을 구성해 첫 프레임을 렌더할 때까지다. 이후에는 범위를 대입한 뒤 오프스크린 위젯을 QImage에 그리는 비용을 잰다. Qt 수치는 입력 전달이나 디스플레이 프레임 대기를 포함하지 않으므로 웹의 입력 지연과 직접 동등한 지표로 해석할 수 없다.

범위는 6회 시험의 최솟값과 최댓값이다. 마지막 행은 그리기 호출 자체를 제외한 대기 시간이다. 각 열의 p95는 구간별로 따로 계산했으며 합산해 전체 p95를 구할 수 없다. 4개 plot의 압축 없는 JSON 본문은 첫 표시 181,858 B, 이동·확대에서 179,618–185,211 B였다. 최초 요약을 만든 뒤 4채널 조회 비용이 줄었고 자식 왕복 부가 시간은 p95 1 ms 미만이었다. HTTP 수신과 인코딩에도 시간이 들지만, 입력 이벤트 처리 전후와 프레임 일정 대기가 큰 구간으로 관측됐다.

Qt의 `Viewer::open`(파일 열기와 신호 연결)은 52.49–60.45 ms였다. Windows가 기록한 프로세스별 피크 working set은 Qt 뷰어 약 195.3–195.4 MiB, 웹 CLI 약 186.5–186.6 MiB, Node 약 61.6–65.8 MiB, Chromium 브라우저 프로세스 약 131.2–133.9 MiB, 시험별 최대 렌더러 약 131.6–134.6 MiB였다. 프로세스별 피크 발생 시점이 다르다.

## 후속 시험 · 입력과 Canvas 그리기 예약

같은 데이터, Windows headful Chromium, 1280×780과 DPR 1, warm OS cache에서 경로 3개를 교차 실행했다. 경로마다 형식별 3회, 회차마다 같은 드래그 25회와 휠 25회를 시험했다. React는 Canvas와 리스너를 처음 구성하고, 이벤트 콜백이 범위를 바꿔 바로 조회를 시작한다. 후속 경로는 휠을 passive로 받고 CSS에서 기본 스크롤과 오버스크롤을 막았다. 입력 콜백에서 직전 정확한 요약을 새 시간 범위에 투영해 Canvas에 미리 그린 뒤, 해당 범위의 서버 요약으로 교체한다.

- **기존 경로.** 기존 휠 리스너, 미리보기 없이 응답 뒤 rAF에서 그리기.
- **후속 예약형.** passive 휠과 미리보기, 응답 뒤 rAF에서 그리기.
- **후속 즉시형.** 같은 passive 휠과 미리보기, 응답이 준비되면 Canvas에 바로 그리기.

세 경로 모두 입력의 `event.timeStamp`부터 정확한 Canvas를 그린 뒤 처음 실행되는 rAF까지 잰다. 후속 두 경로는 정확한 응답이 같은 기회에 미리보기를 덮는 표본을 미리보기 집계에서 제외하도록 했으며, 이번에는 600개 입력 모두 미리보기 프레임이 따로 관측됐다. 이슈 #24는 정확한 요약 프레임 p95 ≤33 ms로 판정했다. rAF는 브라우저의 프레임 시점을 나타낸다.

예약형과 즉시형은 같은 종료 시점으로 잰 결과 약 18 ms 차이가 났다. 응답 후 그리기 예약에서 프레임 한 번의 대기가 줄었다. passive 휠로 바꾼 뒤에도 휠 입력에서 요청까지 약 36 ms가 걸렸다. 즉시형의 C++ 조회 p95는 4.0–4.8 ms, 직렬화는 4.0–4.3 ms, HTTP·브라우저 수신 중 자식 왕복을 뺀 시간은 12.9–13.3 ms, Canvas 그리기는 0.7–0.8 ms였다. 기존 CSV 첫 회차의 정확한 프레임 p95 83.5 ms에는 HTTP·브라우저 수신의 p95 24.2 ms도 관측됐다. 표에 이 회차를 포함했다.

18회 모두 페이지가 `visible`이었고 입력과 프레임에서 `document.hasFocus()`가 참이었다. 브라우저에는 occlusion·백그라운드 조절을 끄는 Playwright 기본 인수 3개를 전달하지 않았다. Windows 세션은 연결 해제 상태였고, 약 10 ms 간격의 Win32 조회 7,927건에서 `GetForegroundWindow`는 모두 빈 핸들을 반환했다. 시험 직전·직후 각 24개 rAF 간격의 중앙값은 17.7–18.1 ms, 회차별 p95는 18.1–19.1 ms였다. 이 구간에서 긴 간격의 백그라운드 제한은 관측되지 않았다. 연결된 Windows 전경 창과의 비교는 미검증이다.

두 형식에서 피크·인접 원본값·XY 단언을 다시 통과했다. 별도의 Playwright 확인에서 첫 응답을 보류하는 동안 Canvas 픽셀이 미리보기로 바뀌었다. 새 범위의 정확한 결과 이후 먼저 보낸 응답을 풀어도 최신 프레임의 픽셀이 유지됐다.

## 정확도와 범위

- 두 형식 모두 전체 시간 범위의 Canvas 입력에 `a`의 `[행 256, 시각 256, 값 23]`이 남았다. 별도 원본 조회로 행 255·256·257의 값 0·23·0을 확인했다.
- 두 형식 모두 XY Canvas 입력의 원본 행 번호가 엄격히 증가했다. 행 512–515에서 `(4,0) → (0,3) → (-4,0) → (0,-3)`을 보존했고, 앞뒤 원점 표본을 포함한 폐곡선의 부호 있는 면적은 18이었다. 이 검사는 합성 루프 하나를 대상으로 한다. 같은 축약 구간에 여러 작은 루프가 있는 임의 XY는 별도 검증이 필요하다.
- Windows Chromium의 두 파일 창 콘텐츠 캡처에서 4개 시간 plot과 XY가 한 화면에 들어오고 축·범례·단일 피크와 XY 궤적을 식별할 수 있음을 확인했다. 전체 시간 범위에서 피크가 왼쪽 축에 붙어 보여 정확한 시각·값은 원본 조회로 대조했다.
- 물리 디스플레이 표시 완료, cold OS cache, 다른 화면 배율, Electron, 실제 Litzio Host의 invoke 및 복잡한 CSV는 이번 수치의 범위 밖이다.

## 재현

실험 코드 브랜치에서 PowerShell의 `PATH` 앞에 MSYS2 UCRT64의 `bin`을 추가한 뒤 실행한다. 데이터, 캡처와 시험별 JSON은 무시되는 빌드 폴더에 생성된다.

```powershell
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure
New-Item -ItemType Directory -Force build/wave-spike | Out-Null
./build/wave-test.exe --fixture build/wave-spike
npm --prefix spikes/waveform ci
$env:PLAYWRIGHT_SKIP_BROWSER_GC = '1'
Push-Location spikes/waveform
npx playwright install chromium --no-shell
Pop-Location
npm --prefix spikes/waveform run build
node spikes/waveform/benchmark.mjs build
# 기존·예약형·즉시형 후속 측정
node spikes/waveform/benchmark.mjs build compare
```

1차 실험 코드 Release 빌드는 성공했다. CTest는 9/10 통과했고 `studio`의 기존 PDF 비교가 `selection or zoom changed PDF`로 실패했다. 같은 빌드 폴더에서 main 소스로 재구성한 전체 CTest는 10/10 통과했다. 후속 실험 코드의 전체 CTest도 10/10 통과했다.

후속 확인에서는 main `e3057929e9ce1535e8c02050dd6cbf9c6e7bdc4f`의 Release 빌드에서 `ctest --test-dir build -R '^studio$' --output-on-failure`를 별도 프로세스로 5회 실행했다. 5회 모두 통과(1.06 / 0.93 / 0.92 / 0.93 / 0.93 s)해 main에서 같은 PDF 실패를 재현하지 못했다. 간헐 여부와 실패 원인은 미확정이다.
