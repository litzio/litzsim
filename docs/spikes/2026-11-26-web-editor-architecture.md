# 웹 회로 편집기와 공통 코어의 경계

2026-11-26 · 이슈 #22 설계안. 첫 구현은 기존 C++ 회로 코어와 실행기를 유지하고, 한 React 편집기를 브라우저·Electron·Litzio에서 연다. 엔진 언어 선택은 웹 전환 후의 결정이다.

## 1. 누가 무엇을 소유하는가

| 판정 | 근거 |
| --- | --- |
| **채택 · 화면 소스 하나, 로컬 작업 하나** | 같은 벅 회로를 단독 앱에서 그리거나 플러그인으로 열어도 단자 연결과 저장 결과가 같아야 한다. |
| 연기 · 독립 상주 daemon, 자체 SDK·플러그인 등급 | 지금 필요한 호출자는 로컬 편집기와 CLI다. 별도 설치 서비스의 수명이나 제3자 플러그인을 관리해야 하는 사례가 없다. |

| 소유자 | 책임과 호출 경계 |
| --- | --- |
| React 화면 | 탭별 선택·포커스·미저장 표시, 드래그 미리보기, 도면·파형 그리기를 맡는다. 드롭 시 목표 격자점이나 단자 ID를 보내고 확정된 문서를 그린다. 픽셀 교차로 네트를 만들지 않는다. |
| 로컬 작업 | 폴더·파일 선택 결과 처리, 탭 작업본과 Undo, 저장 시 충돌 확인, 실행 디렉터리·자식 프로세스, 파형 구간 읽기를 맡는다. 브라우저 시험과 Electron은 앱 수명의 로컬 HTTP 진입점을 공유한다. 플러그인은 같은 처리 함수를 Node에서 호출한다. |
| 공통 코어 | 부품 정의, 단자·네트·측정 방향, 배치 좌표 변경, 문서 검증·직렬화를 소유한다. 기준 구현은 `src/circuit.{h,cpp}`다. 입력 장치·경로 선택·실행 수명은 호출자가 맡는다. |
| 해석 엔진 | 확정한 회로·제어·초기조건으로 시간축과 신호를 계산한다. 현재 `src/solver.cpp`, `src/pfc.cpp`를 기존 CLI 자식으로 호출한다. 화면 객체나 엔진 포인터가 경계를 넘지 않는다. |
| CLI | 입력을 해석해 같은 편집 연산 또는 실행기를 호출하고 ID·진단·결과 경로를 돌려준다. 기존 `inspect/copy/run/import-csv/export`의 호출 형식은 유지한다. |
| Electron 셸 | 단독 앱의 창과 로컬 작업 프로세스를 열고 닫는다. React 편집기에서 Electron API를 직접 호출하면 브라우저 시험을 할 수 없다. |
| Litzio 플러그인 | `screen.jsx`는 주입된 React와 `pickPath/invoke`를 공유 화면에 연결한다. `host.mjs`는 manifest에 선언한 공용 작업을 로컬 처리 함수에 연결하고 실행기를 찾는다. 회로 의미는 LitzSim에, Litzio 문서 저장은 Litzio에 둔다. |

**차용 근거.** 아래 경로는 [검토한 Litzio 소스](https://github.com/litzio/litzio/tree/cbb6d85fd556a7d864f87b3aebc8025c81dd48c9) 기준이다.

| Litzio의 근거 | LitzSim에서 막는 문제와 적용 범위 |
| --- | --- |

| `docs/adr/0016-shared-local-daemon-host.md`, `0017-bundled-client-and-official-ai.md`(같은 폴더), `apps/editor/server/host-cli.ts` | 창에 실행기 경로·파일 처리가 들어가면 브라우저에서 실행할 수 없다. 셸과 로컬 작업을 분리한다. 단독판에 공유 daemon이나 공식 비서 런타임까지 만들지는 않는다. |
| `docs/adr/0019-plugin-tiers.md`, `docs/adr/0020-plugin-architecture.md`, `docs/adr/0022-plugin-screen-code.md`, `packages/plugin-sdk/src/index.ts`, `docs/design/plugin-screens-v1.md` | 웹 화면은 네이티브 파일을 직접 열 수 없다. Litzio 안에서는 기존 SDK의 화면·Node 호출 경계를 이용한다. 공급 등급이나 플러그인 로더를 LitzSim에 복제하지 않는다. |

## 2. 편집 요청 하나로 벅 회로 바꾸기

| 선택 | 판정 근거 |
| --- | --- |
| **기존 C++ 코어를 CLI로 노출** | `Circuit::insert/move/rotate/setParameter/connectPins/disconnectPin/erase/setWireBend`가 이미 있다. 먼저 한 배치당 CLI 한 번으로 비용을 실측할 수 있다. |
| WASM 빌드 | 같은 소스를 쓸 수 있지만 Qt Core와 파일 I/O 분리·브라우저 빌드가 먼저 필요하다. 네이티브 왕복이 편집을 막을 때 재검토한다. |
| 임시 TypeScript 편집기 | 웹에서 단자·극성·직렬화를 다시 구현하면 공통 코어 원칙을 위반한다. 한시적 구현으로도 채택하지 않는다. |

제안하는 최소 서명은 `apply(document, expectedRevision, operations[]) → {document, receipt} | error`다. CLI는 JSON 입력·출력으로 감싸고 화면은 같은 입력을 로컬 계층에 보낸다. 공개 서명에 Qt 타입을 넣지 않는다.

- 연산은 `add(type, grid?)`, `move(id, grid)`, `rotate(id)`, `setParameter(id, key, value)`, `connect(part.pin, part.pin)`, `disconnect(part.pin)`, `delete(id)`다. 값 키에는 기존 파일의 단위가 들어간다. 새 부품 ID와 단자명은 결과에서 읽어 다음 요청에 쓴다.
- 코어는 작업본 사본에 순서대로 적용하고 구조를 검증한다. 미접속 단자는 저장할 수 있고 실행 직전에 실행 가능성을 따로 검사한다. 알 수 없는 단자·파라미터는 실패 연산 번호와 대상 ID를 반환하며 앞선 편집도 버린다.
- receipt에는 변경 전후 revision, 생성·변경·삭제된 ID와 바뀐 네트의 전후 단자 목록을 담는다. 두 단자를 이었을 때 예상한 가지가 바뀌었는지 AI도 판독할 수 있다. 실행 로그나 범용 receipt 저장소는 필요하지 않다.
- 탭은 현재 Qt의 `Revision`처럼 배치 전 문서를 한 번 보관한다(`src/studio.cpp`). Undo 요청은 현재 revision과 receipt의 변경 후 revision이 일치할 때만 직전 스냅샷을 한 번에 복원한다. CLI 파일 편집도 요청자가 보관한 전 문서와 receipt로 같은 검사를 거친다.
- 작업본 revision과 마지막으로 읽은 디스크 revision을 구분한다. 같은 파일을 쓰는 로컬 작업과 CLI는 파일별 저장 구간에서 버전 확인과 교체를 직렬화한다. 외부 변경으로 저장이 거절되면 작업본을 유지하고 두 버전을 보여준다. 파일 v1에는 revision이나 Undo 필드를 추가하지 않는다.

## 3. AI가 RC 회로를 읽고 고치는 순서

| 경로 | 판정 근거 |
| --- | --- |
| **파일·CLI와 짧은 스킬** | 저장된 회로만 있어도 작업을 재현할 수 있다. 플러그인 안에서는 같은 작업에 Host 입력 검증과 receipt가 붙는다. |
| 화면 좌표 클릭 자동화 | 화면 배율에 따라 같은 점이 다른 단자를 가리킨다. AI의 편집 계약으로 쓰지 않는다. |

1. 스킬에 대상 파일, 단위·극성 확인, 편집 전 revision 읽기, 실패 후 재읽기 순서를 적는다. `examples/rc.litzsim`의 `output`에는 `R1.n, C1.p, VC.p`가 있고 `VC.n`은 접지에 있다. 텍스트와 부품 정의만으로 전압계의 두 기준점을 확인할 수 있다. 현재 `inspect`는 미접속 핀만 출력한다. 제안하는 JSON 조회는 코어가 해석한 단자·네트·측정 방향과 revision을 반환한다.
2. 예컨대 `apply`로 R1의 `resistance_ohm`을 바꾸고 receipt에서 연결이 보존됐는지 읽는다. 좌표 없는 추가는 빈 격자점 선택을 공통 배치 연산에 맡기고, 연결은 이름 붙은 단자로 지정한다. 자동 정렬은 선택된 부품만 이동하여 PFC의 손대지 않은 레그 위치를 보존한다. GUI도 같은 배치 연산을 호출한다. [Simulink 편집 도구와 선행 설계](2026-11-25-circuit-editor.md)
3. 제안할 CLI 작업 `start/status/stop`은 실행 중인 앱의 로컬 관리자에 연결한다. 앱 없이 실행할 때는 기존 동기식 `run INPUT OUTPUT.wave`를 사용한다. 완료된 run의 신호·단위·시간 범위를 읽고 원본 행을 조회해 전후 값을 비교한다. 조회한 run ID와 시간을 함께 보고한다.
4. Litzio 비서는 사용자가 지정한 파일과 플러그인 스킬을 쓴다. 조회는 `assistant:true` 읽기 작업이나 healthCheck로 노출한다. 편집·실행·중지는 승인 및 CLI guard가 허용할 때 공식 CLI의 `operation invoke <id> --input <json-file> --host <origin> --json`으로 같은 host.mjs 작업을 부른다. 화면 전용 handler나 미저장 탭을 비서가 암묵적으로 대상으로 삼지 않는다. 저장 파일이 바뀌면 화면에 다시 읽기 또는 저장 충돌을 표시한다. 근거는 Litzio의 `docs/adr/0021-general-agent-assistant.md`, `apps/editor/server/assistant-cli.ts`, `docs/design/plugin-stage1-v1.md`다.

## 4. 실행 수명과 보관할 결과

| 선택 | 판정 근거 |
| --- | --- |
| **접수한 뒤 run ID로 조회** | 플러그인 일반 호출은 10초 제한이다. 호출이 끝나도 로컬 실행 관리자가 자식과 결과를 소유해야 중지할 수 있다. 근거는 Litzio의 `docs/design/plugin-stage1-v1.md`다. |
| 완료까지 호출 유지 | 회로의 종료 시각을 늘리면 정상 실행도 호출 시간 초과가 된다. |

- 현재 `Studio::startRun/recordRun/stopRun`이 회로 파일 옆 `runs/<uuid>/circuit.litzsim`, `status.json`, `result.wave`를 관리한다. GUI의 현재 작업본을 복제하는 관례를 유지한다. AI가 파일을 지정하면 읽은 저장본을 복제한다. 이후 편집은 해당 실행 입력을 바꾸지 않는다.
- start는 스냅샷과 상태 기록에 성공하고 자식을 접수하면 ID를 즉시 반환한다. 화면·CLI는 짧은 status 호출로 running/stopping/completed/canceled/failed와 메시지를 본다. 초기에는 단계만 표시한다. 엔진이 계산 시각을 제공할 때만 진행률을 표시한다. 시간 초과 뒤 접수 여부가 불명확하면 기존 run을 확인한 뒤 재실행한다.
- stop은 해당 자식만 중지한다. 종료 확인 후 취소/실패를 기록하고, 정상 종료와 완성된 파일을 모두 확인한 경우만 결과로 연다. 첫 버전은 기존처럼 관리자당 동시 실행 하나다. 화면을 다시 열면 상태 파일을 읽고, 관리자가 정상 종료·플러그인 reload할 때는 자식을 정리한다. 비정상 종료 뒤 소유자를 확인할 수 없는 기록은 진행 중으로 단정하지 않는다.
- 문서에 넣을 때 사용자가 run과 저장한 그림을 고른다. 상대 경로(예: `runs/<id>/result.wave`), 신호·단위·구간을 문서에 남기고 필요하면 정적 그림을 첨부한다. 회로도는 SVG/PDF로 별도 저장한다. Litzio에서 새 결과 문서를 만들 때는 `saveDocument`의 공식 작성 입력을 쓰고, 기존 문서에는 사용자가 참조를 넣는다. 문서를 열 때 해석기를 실행할 필요가 없다. 근거는 Litzio의 `docs/design/plugin-screens-v1.md`다.

## 5. 파형 데이터가 화면에 도착하는 경로

| 선택 | 판정 근거 |
| --- | --- |
| **로컬에서 보이는 구간만 조회** | `src/waves.{h,cpp}`에 이미 파일 매핑, 극값 행 인덱스, `envelopeRows/envelope/at`가 있다. 파일을 열린 동안 유지해 신호별 요약을 재사용한다. |
| CSV 전체를 브라우저 배열로 전달 | 1,000만 행의 파싱·복사·메모리 비용을 화면마다 지불한다. |

CSV는 기존 `importCsv`로 한 번 변환한다. React는 run·신호·시간 범위·그리기 폭을 보내고 로컬은 픽셀 구간별 극값의 원래 행·시각·값을 시간 순서로 돌려준다. 이동 중 늦게 온 이전 범위 응답은 버린다. 커서값·통계는 원본 행에서 구한다. XY는 같은 행의 X·Y를 읽어 취득 순서를 유지한다. 비단조 X에 시간 plot의 최소·최대 축약을 그대로 적용하면 루프가 사라질 수 있어 별도 판정한다.

[기존 측정](../reviews/pfc-validation.md)은 준비 파일·warm cache·1280×780에서 Qt 첫 4 plot 282–334 ms, 범위 이동 p95 10.29–11.18 ms였다. 웹 인수 시험은 [MVP](../mvp.md)의 동일 1,000만 행 × 8신호와 시간 열, 엔진 파일·CSV 변환본을 쓴다. Windows CPU·RAM·SSD·배율, Release 빌드·브라우저 버전·캐시 조건을 기록한다. CSV 변환, 재열기, 첫 화면, 프로세스별 최대 메모리를 분리한다. 3회 각각 4 plot 첫 표시 ≤2초, 50회 이동·확대 입력부터 그린 프레임까지 p95 ≤33 ms를 브라우저와 실제 배포 화면에서 측정한다. 블록 경계 단일 피크와 양옆 원본값, 비단조 XY의 순서·루프도 확인한다.

## 미검증 가정

- 플러그인 설치본에서 네이티브 실행기를 찾고 두 화면에서 같은 React 번들을 로드하는 경로는 실제 Host 시험이 필요하다. Litzio의 `PluginContext.cli`는 Litzio 공식 CLI를 가리킨다. LitzSim 실행 파일의 위치를 보장하지 않는다(`docs/design/plugin-stage1-v1.md`).
- 브라우저 전송·렌더 비용, CLI 배치 호출의 체감 지연, 선택 범위 자동 배치의 도면 품질, PDF 글꼴·실물 인쇄 품질은 구현 전에는 알 수 없다. 기존 Qt 벤치마크와 출력 기록으로 웹 결과를 대신할 수 없다.
